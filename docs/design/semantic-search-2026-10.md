# 意味検索（スクラップの索引）の設計

状態（2026-10-02）: **P0（字句検索の改善）と P1（`pkg/embed`、`pkg/semindex`、CLI）を実装済み**（まだコミットしていない）。P2 以降（アプリ内の更新処理、設定画面、GUI）は未着手。実装の記録と実測は §15。決めること（§13）が残っている。

## 1. 目的と、やらないこと

**目的**: 「前になんとなく書いた、あの話」を、言い換えた言葉でも引き出せるようにする。人が使う検索（Ctrl+Shift+F）と、エージェント（`{{ @claude-code … }}`、CLI 経由）が過去のメモを引く記憶の両方に使う。

**やらないこと**:
- 本体の軽さを損なうこと。使わない設定では、プロセスも、メモリも、ディスクも、何も増えない。
- 常駐の監視プロセス、サーバー型の DB、CGO、C++ のライブラリを足すこと（Windows は CGO なし、Mac はユニバーサルビルド、CI は CGO なしのビルドも検査している）。
- ベクトルを Git で同期すること。Markdown が正本で、索引は端末ごとに作る派生データ。
- 意味検索を完全一致の検索の代わりにすること。完全一致は、そのまま残る。

## 2. 実験で分かったこと（設計の根拠）

サンプルは、300 日分・1,829 件のスクラップ（テンプレートから作成、正解が分かる 31 件、意味検索 28 問）。モデルは bge-m3（Ollama）。**テンプレート由来で、正解が短い 1 文のため、数値は傾向として読む。実データでの再評価が必要（§12）。**

| 方法 | hit@1 | hit@5 | MRR |
|---|---|---|---|
| 字句（文字 2 字組の BM25） | 0.46 | 0.61 | 0.51 |
| ベクトル 600 字、見出しなし | 0.54 | 0.57 | 0.56 |
| ベクトル 600 字、見出しあり | 0.57 | 0.68 | 0.63 |
| ベクトル 150 字、見出しなし | 0.64 | 0.75 | 0.69 |
| ベクトル 150 字、見出しあり | 0.79 | 0.82 | 0.81 |
| 150 字、見出しあり、順位融合（RRF） | 0.61 | 0.61 | 0.63 |
| 150 字、見出しあり、**cosine + 0.05 × 正規化 BM25** | **0.82** | **0.89** | **0.86** |

設計に効く結論:
1. **埋め込む文の先頭に、日付と見出しを付ける**（+0.15 前後）。
2. **チャンクは小さめ（約 150 字）から始める。** 300 字以上では差が出なかった。ヒットしたら、前後の文や、その 1 件全体を返す（小さく索引し、大きく返す）。
3. **融合は、順位ではなく点数。** cosine に、小さな重みで BM25 を足す。RRF は、BM25 が外れたときにベクトルの正解を引きずって悪化した。
4. IP アドレスのような識別子の検索は、どの方法でも満点（完全一致の検索が、今も補う）。
5. 速度（Ryzen 7 8845HS）: 埋め込みは GPU で約 85 件/秒、CPU のみで約 29 件/秒（短文）。モデルの初回ロード約 1.7 秒、ロード済みのクエリ埋め込み約 85 ms。総当たりの検索は、5 万チャンク × 1,024 次元で 15 ms（16 スレッドで 4 ms）、20 万チャンクで 60 ms。**近似検索（HNSW）は要らない。**

## 3. 全体像

```
Markdown（正本、Git で同期）
   │  ① 一覧と指紋（mtime、サイズ、内容のハッシュ）
   ▼
チャンク化（見出しの文脈つき）──② 内容ハッシュで差分 ──▶ 埋め込み（Embedder）
                                                       │ ローカル（Ollama）/ クラウド
   ┌───────────────────────────────────────────────────┘
   ▼
索引（端末ごと、リポジトリの外）: chunks（メタデータ）＋ vectors（float32 か int8）
   ▲                                    │
   │ ③ トリガー（§7）                    ▼
 アプリ（空き時間）/ CLI（scrap index）   検索: cosine ＋ 0.05 × BM25 ＋ 絞り込み ＋ 未索引分は完全一致で補う
```

- パッケージ: `pkg/embed`（Embedder と、各プロバイダー）、`pkg/semindex`（チャンク化、保存、検索、更新）。どちらも純 Go。
- 入口: `md-memo scrap index` と `scrap search --semantic`（アプリが起動していなくても動く）、JSON-RPC のメソッド（起動中のアプリが、索引をメモリに載せて速く答える）、設定画面（§9）。

## 4. 設定

`config.semantic`（フロントエンドが保存する生の JSON。Go 側に型を足すのは、読み出しの部分だけ）。**既定は、すべてオフ。**

```jsonc
"semantic": {
  "enabled": false,
  "model": { "baseUrl": "http://localhost:11434", "model": "bge-m3", "apiKey": "", "dimensions": 0 },
  "indexOn": "idle",                 // "idle"（空き時間に随時）| "daily"（1 日 1 回）| "manual"（手動だけ）
  "schedule": { "dailyAt": "03:00", "onlyOnAC": true, "idleMinutes": 10, "settleMinutes": 10, "catchUpAtStart": true },
  "limits": { "monthlyTokens": 20000000, "concurrency": 2 },
  "privacy": { "cloudConsent": { "host": "date" }, "excludeKinds": ["ai"], "logChars": 1000 }
}
```

- `model` の枠は、既存の枠（text、vision、voice）と同じ形。プロバイダーは、接続先のホストとモデル名から判定する（`embed.DetectProvider`。`generativelanguage.googleapis.com` かモデル名が `gemini…` は Gemini、ポート 11434 かホストに `ollama` を含み `/v1` のないものは Ollama、それ以外は OpenAI 互換 `/v1/embeddings`）。**Ollama の既定でないポートで動かすときは、OpenAI 互換と読まれる**ので、`baseUrl` に `/v1` を付ける。
- **キーの継承は、ホストが同じときだけ**（C10-14 の修正と同じ規則）。text 用の OpenAI のキーを、意味検索の枠が別のホストに使うことはない。**実装済み**: `semantic.model.apiKey` → 同じホストの `text`、`vision`、`autocomplete` のキー → 環境変数 `MD_MEMO_EMBED_API_KEY`（設定ファイルにキーを置かずに済む）。
- **実装済みの読み出し**（`semindex.ParseConfig`。アプリからも同じ関数を使う）: `enabled`、`model`、`schedule.settleMinutes`（既定 10）、`privacy.cloudConsent`（`{"ホスト": "日付"}`。https はホスト、http は `http://ホスト` を鍵にする。既存の同意と同じ規則で、https の同意が http を許すことはない）、`privacy.excludeKinds`（既定で AI の結果を除く）。ほかの項目（`indexOn`、`limits`、`onlyOnAC` など）は P2。
- `dimensions`: 0 はモデルの既定。OpenAI（256〜1536）と Gemini は、次元を減らせる（保存量と速度を下げる用途）。変えたら、索引は作り直し。

## 5. プロバイダー（Embedder）

```go
type Embedder interface {
    ID() string   // 索引に記録する識別子: "ollama|bge-m3|1024"
    Dim() int
    Caps() Caps   // 扱える種類: テキスト／画像（／音声、PDF）、1 回の上限（件数、トークン）
    Embed(ctx context.Context, kind Kind, in []Input) ([][]float32, error) // Kind: Document | Query。Input は、テキストか画像（バイト列と MIME）
}
```

| プロバイダー | 呼び出し | 備考 |
|---|---|---|
| Ollama | `POST /api/embed`（`input` は配列、`keep_alive`） | 既定の候補は `bge-m3`（多言語、1,024 次元）。バッチは 16〜32、`keep_alive` は数分 |
| OpenAI 互換 | `POST {base}/embeddings`（`model`、`input`、`dimensions`） | OpenAI、LM Studio、vLLM など。`text-embedding-3-small` は 100 万トークンあたり約 $0.02（Batch は半額）、1 回に最大 2,048 件、1 件 8,191 トークン |
| Gemini | `embedContent` / `batchEmbedContents`（`outputDimensionality`） | 実装時に、公式の最新の仕様（モデル名、タスク種別の指定方法）を確認する。Batch API は半額で、24 時間以内に完了する非同期 |

- **Query と Document を区別する**: e5 系は接頭辞（`query: ` と `passage: `）、Gemini はタスク種別が要る。Embedder が吸収する。
- **受け取ったベクトルは、L2 正規化してから保存する**（次元を減らした場合を含む）。
- **再試行**: 429 と 5xx は、`Retry-After` と指数バックオフ。タイムアウトは、リクエストごと。失敗したチャンクは、次回に回す（索引全体は壊れない）。
- **最初のバージョンは、同期 API だけ**。プロバイダーのバッチ API（OpenAI、Gemini。半額、24 時間以内）は、ジョブの管理が要るのに、個人の規模では差が小さい（10 万チャンク ≈ 1,000 万トークン ≈ 数十円〜 $1.5）ので、後回し（§11 の P4）。
- Anthropic には、埋め込みのモデルがない。クラウドは、OpenAI 互換と Gemini から始める。Voyage、Cohere などは、OpenAI 互換の形で使えるものから足す。

## 6. 索引

**保存場所**: `%APPDATA%\md-memo\index\<id>\`（Mac は `~/Library/Application Support/md-memo/index/<id>/`）。**スクラップのフォルダの中には、置かない**（Git 連携は `git add .` でフォルダ全体をコミットするので、置くとベクトルが push される）。`<id>` は、Git のリモートの URL から決める（フォルダの名前や場所を変えても、作り直さない）。リモートがなければ、フォルダの絶対パスから決める。

**ファイル**:
- `manifest.json`: 版、Embedder の ID（プロバイダー、モデル、次元）、チャンク化の版、ファイルごとの指紋（相対パス、サイズ、mtime、内容のハッシュ）、月ごとの使用トークン。原子的に書き換える（`pkg/atomicfile`）。
- `chunks.jsonl`: チャンクのメタデータ（相対パス、行の範囲、日付、見出しの経路、種類、内容のハッシュ、本文）。
- `vectors.bin`: ヘッダ（次元、件数、float32 か int8）＋ 行ごとのベクトル。`chunks.jsonl` と同じ順。
- `index.lock`: 書き込み中の印（PID つき）。アプリと CLI が、同時に更新しない。

**チャンク化の規約**（実験の結果が出発点。実データで調整する）:
1. 構造で切る: `---` と見出し（H1〜H3）。CLI パイプの 1 件（`## [時刻] CLI Pipe`）が 1 単位。
2. 約 150 字に整える: 段落、次に「。」で切る。長い段落の途中で切るときだけ、1 文を重ねる。極端に短いものは、同じ見出しの隣と結合する。
3. **文脈の見出し**: 埋め込む文の先頭に、`日付 > 見出し` を付ける。保存する本文には、付けない。
4. 種類ごとの扱い: 通常のメモは、そのまま。**CLI パイプのログは、先頭 1,000 字とコマンド名だけ**。**AI の結果ブロック（`md-memo:res`）は、既定で除外**（AI の文を再検索すると、同じ内容が循環する）。HTML コメントは除く。タスク行（`[[ @llm … ]]`）は、指示文として残す。
5. **返すときは大きく**: ヒットしたチャンクの前後の文、または 1 件全体を返す。

**増分更新**: ファイルの指紋（mtime とサイズ）が変わったものだけ、チャンク化し直す。チャンクの内容ハッシュ（見出しつきの本文＋Embedder の ID＋チャンク化の版）を、保存済みのものと比べ、新しいハッシュだけ埋め込む。日付のスクラップは追記が主なので、末尾の分だけが対象になる。名前の変更や重複した内容は、ハッシュで再利用する。削除されたファイルは、印を付けて、不要な行が 2 割を超えたら詰める。

**除外**: `.git`、`assets`、競合のコピー（`… (sync conflict … ).md`）は、既定で対象外。スクラップのフォルダの `.md-memo-ignore`（1 行 1 パターン、`#` はコメント）で、フォルダやファイルを除外できる（このファイルは Git で同期され、2 台で揃う）。

**サイズ**: 1,024 次元・float32 で、5 万チャンクが 205MB。int8 にすると約 50MB、256 次元にしても約 50MB。**int8 を、保存形式の既定にするかは、実データでの精度で決める**（§12）。

**モデルやチャンク化の版が変わったら、索引全体を作り直す**（古い索引は、作り直しの完了まで使い続ける）。索引は派生データなので、壊れたら、いつでも作り直せる。

## 7. 処理のタイミング（トリガー）

**打鍵や自動保存のたびには、行わない。**（モデルのロードに約 1.7 秒、メモリ約 1.2GB。編集の途中の状態を埋め込むのは無駄。）常駐の監視プロセスも持たない。トリガーは、すべて「機会があったときに、ファイルの指紋を見る」形（数千ファイルの stat は数 ms）。

| # | トリガー | 動き |
|---|---|---|
| T1 | **落ち着いた**: ファイルが `settleMinutes`（既定 10 分）変更されていない | そのファイルの差分を処理。今日のスクラップの末尾の 1 件は、区切りが付く（次の `---` か見出し）まで待つ |
| T2 | **空き時間**: 入力が `idleMinutes`（既定 10 分）止まった（`indexOn: "idle"`） | 未処理の分を、小さなバッチで処理。入力があれば、現在のバッチで止め、あとで再開 |
| T3 | **毎日**: `dailyAt`（既定 03:00）（`indexOn: "daily"`） | 1 日分をまとめて処理。PC が止まっていたら、`catchUpAtStart` で、次の起動後、最初の空き時間に実行 |
| T4 | **同期のあと**: Git の取り込みで、ファイルが変わった | 変わったファイルを、次の T1〜T3 の機会に処理 |
| T5 | **手動**: `md-memo scrap index`（`--status`、`--rebuild`）、設定の「今すぐ更新」 | 即時。タスクスケジューラや launchd からも呼べる |
| T6 | **検索のとき** | 待たせない。索引済みの分は意味検索、未索引の分は完全一致で補い、「N 件が未索引」と出す。`--update` を付けたときだけ、時間の上限（既定 3 秒）つきで更新してから検索 |
| T7 | **初回の構築** | 利用者が始める。進捗を表示し、中断と再開ができる。CPU のみで 10 万チャンクは約 1 時間の見込み |

**実行してよい条件（すべて満たすとき）**: 機能がオン／同意済み（クラウドの場合、§8）／Embedder に届く（Ollama が動いている。**こちらから起動はしない**）／索引のロックが取れる／`onlyOnAC` が真なら電源に接続／月の上限（`monthlyTokens`）に達していない／（T2 では）入力が止まっている。

**既定の考え方**:
- **ローカルのモデル**: 追加の費用がないので、`idle`（T1 と T2）が既定。毎日のバッチにする理由が弱い。
- **クラウドのモデル**: 呼び出しが少ないほうが予測しやすいので、`daily` を勧める。ただし、利用者が選べる。初回の構築の前に、概算の件数と費用を見せる。
- **ノート PC**: `onlyOnAC` の既定は真。バッテリーでは、手動だけ。

**資源への配慮**: 小さなバッチ（16〜32 件）で、間にスリープを入れる。`concurrency` は 2 まで。Ollama には、`keep_alive` を短く（数分）指定し、バッチが終われば、モデルをメモリから外す。ネットワークは、クラウドのときだけ使う。

**空き時間と電源の検知**（今のコードにはない）: Windows は、`GetLastInputInfo`（最後の入力からの経過）と `GetSystemPowerStatus`（電源）。Mac は、`ioreg` の `HIDIdleTime` と `pmset -g batt`（実行して読む。CGO は使わない）。取れないときは、「ウィンドウが非アクティブになってからの経過」で代える。

## 8. プライバシーとクラウド送信

**既定は、ローカルのモデルだけ。クラウドは、利用者が選んだときだけ。**

- **同意は、有効にするとき 1 回、明示的に取る。** 今の同意（質問バーなど）は、選んだ範囲を、その場で送る話。索引は、**スクラップ全体が、人がいないときに、自動で送られる**ので、種類が違う。同じ `cloudConsent` に混ぜず、`semantic.privacy.cloudConsent`（ホストごと）に別に持つ。ダイアログには、次を書く: 送り先のホスト／送る内容（除外の設定を除く、すべてのチャンク）／いつ送るか（トリガー）／概算の量と費用／クラウド側の保存や学習の扱いは、そのプロバイダーの規約に従うこと／いつでも止められて、索引は削除できること。
- **送る前に、機密を除く**: `pkg/llm/redact.go`（と `secret_strip.js`）の規則で、API キー、トークン、秘密鍵などを含むチャンクは、クラウドへ送らない。
- **除外**: `excludeKinds`（既定で AI の結果）、`.md-memo-ignore`、ログの長さの上限。
- **見えるようにする**: ステータスバーの AI の項目と、設定の「送信先」の行に、「意味検索: クラウド（ホスト）」と出す。ウェルカムのノートと About の「ノートはこのパソコンの外に出ません」の文は、クラウドを有効にしたときの注記を足す。
- **ローカルのモデルでも、索引は端末に残る**: ベクトルは元の文を推測できる。索引はリポジトリの外に置き、ディスクの暗号化は OS に任せる。

## 9. 検索

**CLI**（アプリが動いていなくても使える。JSON 出力あり。エージェントは Bash から呼ぶ。**実装済み**）:

```
md-memo scrap search "サステナブルな建材のアイデア" --semantic [--from 2025-01-01 --to 2025-12-31] [--kind note,log] [--path <パターン>] [--limit 10] [--json] [--update]
md-memo scrap index [--status | --rebuild | --dry-run] [--force] [--settle 分] [--yes]
```

- 日付の絞り込みは、既存の `scrap search` と同じ `--from` / `--to`（YYYY-MM-DD、日付の名前のファイルだけ）。当初案の `--since` / `--until` は採らなかった（同じ意味の旗を 2 組にしないため）。
- `--update`: 検索の前に索引を更新する（上限 3 秒）。`--status`: 設定、索引、未処理のファイル数を表示（モデルを呼ばない）。`--yes`: 外部のホストへ 1,000 チャンク超を送る実行の確認。

- 並べ替え: `cosine + 0.05 × 字句の点`（字句の点は、2 文字の組と英数字の語の BM25 を、「質問の全トークンを 1 回ずつ含むチャンクの点」で割ったもの。当初は「候補の最高点」で割っていたが、日英混在で害があったので変えた。§15）。クエリは、索引と同じ Embedder で埋め込む。
- 絞り込み（日付、種類、パス）は、点数を出す前に、メタデータで行う。
- 結果: ファイル、行、日付、見出しの経路、点数、スニペット、前後の文脈。ファイルは相対パス（2 台の環境で、フォルダの場所が違っても、同じ識別子）。開くときに、手元のフォルダと結ぶ。
- **未索引のファイルは、単語の検索で補う**（T6、実装済み）。新規か変更後のファイルは索引にないので、その分は単語の検索（`--ranked` と同じ）にかける。**全語を含むヒットは先頭**（直前に書いたノートを、意味検索の結果に埋もれさせない。実機で、意味検索が `--limit` を埋めると探せないことが分かって変えた）、一部だけ含むヒットは意味検索のあとに置く。各ヒットの `source` は `semantic` か `words`。
- **モデルや索引が使えないときは、単語の検索に落ちる**（実装済み）。索引が空、別のモデルで作られている、壊れている、モデルに届かない — このときは、`--ranked` と同じ単語の検索の結果を返し、JSON の `notes` と、文章の出力の最後の `note:` に理由を 1 行出す（`semantic: false`）。**設定の問題（機能がオフ、クラウドのホストが未許可、モデル名やキーがない）は、落とさずエラー**にする（人が直すことなので）。

**起動中のアプリ**: 索引をメモリに載せ、RPC（`scrap.search`）で答える（CLI は、アプリが動いていればそちらを使い、いなければ、ファイルを読む）。**GUI**: Ctrl+Shift+F の検索に、「意味」の切り替えを足す（P3）。関連ノートの表示（今はタイトルが中心）にも、近いチャンクを使える。

**スキル**: `skills/md-memo/references` に、エージェント向けの使い方（いつ使うか、`--since` で絞る、結果は引用する）を足す。MCP のサーバーは作らない（CLI で足りる）。

### 設定画面

- **場所とタイトル**: 設定 → AIモデル の末尾に、節「**意味検索**」（英語の画面は「Semantic Search」）を置く。タイトルは、これだけにする（利用者の決定、2026-10-02。ほかの節 — 音声入力、画像生成 — と同じ短さ）。詳細設定の節（「詳細設定を表示」がオンのときに出る）。
- **項目**（サンプルの画面は、作業用の一時フォルダの `mock/` にある）: 「意味検索を有効にする」のスイッチ（既定オフ）／索引の状態のカード（件数、未処理、最終更新、使用量、今すぐ更新、作り直す、索引を削除）／モデルの種類（ローカル（Ollama）、クラウド（Gemini）、クラウド（OpenAI 互換））と、接続先、モデル名、API キー／送信先の行（ローカルは緑、クラウドは黄色の枠）／処理するタイミング（空き時間に随時、1 日 1 回、手動だけ）、実行する時刻、月の上限／電源に接続しているときだけ処理する／AI の結果ブロックを索引に入れない／**「画像」のグループ**（§14）。
- **「画像」のグループ**: 「画像も検索の対象にする」のスイッチ（既定オフ）と、「画像の扱い」の選択。**ローカルのモデル**のとき: 「ノートの文字だけ（標準、G1）」／「画像の説明を作る（視覚モデル、G2）」。G2 を選ぶと、進捗のカード（枚数、残り時間、一時停止）、使う視覚モデル（設定の「画像解析 (OCR)」と同じ）、「画像をこのPCの外に出さない」がオンのときは、クラウドへ送らない旨を出す。**クラウドのモデル**（マルチモーダルのモデルを選んだとき）: 「ノートの文字だけ」／「画像そのものを使う（推奨、G3）」。G3 では、画像は長辺 1,024 px に縮小して JPEG にし、位置情報と撮影日時（EXIF）は送らない旨を出す。モデル名の欄には、画像に対応するモデルかどうかの説明を出す。送信先の枠には、「画像」も送られると明記し、同意のダイアログにも画像（縮小して、位置情報を除く）を書く。
- クラウドを有効にするときは、1 回だけ、確認のダイアログ（§8）を出す。

## 14. 画像（assets）を検索の対象にする

画像は、`<スクラップのフォルダ>/assets/` に置かれ、ノートからは `./assets/…` で結ばれている（貼り付け、ホットフォルダ、Mobile Drop）。ホットフォルダで処理した画像は、OCR の文字が、すでにノートに入っている。OCR できなかった写真は、ファイルだけが assets に残る。文字を持たない写真（物、風景、図）は、今は文字では探せない。次の 3 段階で、段階ごとに入れられる。

| 段階 | 方法 | 追加で要るもの | 探せるもの | 送信 |
|---|---|---|---|---|
| G1 | **ノートの文字で探す**: 画像を参照する項目（OCR の文字と前後の文）が、すでに検索の対象。ヒットに、画像のサムネイルと、ノートへの移動を付ける | なし（P1〜P3 のまま） | 文字のある画像（スクリーンショット、書類、ホワイトボード、レシート） | 追加なし |
| G2 | **画像の説明を作る**: 既存の「画像解析（OCR）」の視覚モデルで、画像ごとに説明と文字を作り、索引に保存して、その文を埋め込む | 視覚モデルの呼び出し（画像 1 枚ごと） | 文字のない写真も、言葉で探せる（「去年の現場の、梁の写真」） | 画像が、視覚モデルへ送られる（クラウドなら、別の同意） |
| G3 | **画像を直接埋め込む**: 画像とテキストが同じ空間に入るモデルで、画像そのものをベクトルにする。文字のない写真も、図も、「似た画像」も探せる | マルチモーダルの埋め込みモデル（下の「G3 の現状」） | 画像の見た目、図、似た画像 | 画像が、埋め込みの API へ送られる（クラウドのモデルのとき） |

**G3 の現状（2026-10 に調べた）**:
- **クラウド**: Gemini Embedding 2（`gemini-embedding-2`）が、テキスト、画像、動画、音声、PDF を、1 つの空間に入れる（128〜3,072 次元、100 以上の言語、入力は合計 8,192 トークン）。第三者の資料では、画像は 1 枚 258 トークン、1 回に画像 6 枚まで、形式は PNG と JPEG。**公式のページでは、画像の上限と形式、料金は確認できていない。実装前に、公式の最新の仕様を確認する。**
- **ローカル（Ollama）**: 公式のライブラリにある埋め込みモデル 12 個は、すべてテキストのみ。**Ollama では、画像の埋め込みは今はできない。**
- **ローカル（Ollama 以外）**: オープンな重みのモデル（Jina Embeddings v4、SigLIP 2、Nomic Embed Vision、GME）は実在するが、Go から使える標準の実行環境（サーバー）が定まっていない。使うなら、別の実行環境（llama.cpp 系、ONNX など）の検証が要る。配布を重くしない形で使えるかは、未確認。

**G3 を入れるときの設計**:
- **1 つのモデルで、テキストと画像を同じ索引に入れる**（マルチモーダルのモデルを選んだとき）。クエリを 1 回埋め込めば、メモの文と画像の両方がヒットする。**ただし、テキストの埋め込みも、そのモデルになる**（クラウド）。日本語のメモでの精度が、bge-m3 と比べてどうかは、未検証（§12 の評価の道具に、そのモデルをつないで測る）。
- **画像と文のモデルが別のとき**（ローカルの bge-m3 ＋ 画像用のモデルなど）は、索引を 2 つに分け、点数を正規化して合わせる。この複雑さを避けるため、最初の対応は、1 つのモデルで済む形だけにする。
- **画像は、送る前に加工する**: 長辺を縮小（既定 1,024 px）し、JPEG に再エンコードする。**EXIF（位置情報、撮影日時）は、再エンコードで落ちるので、送信先へ位置情報が出ない**（プライバシーの利点）。PNG と JPEG 以外（WebP、HEIC、GIF）は、読めるものは変換し、読めなければ対象から外す。
- **費用**: 画像 1 枚が約 258 トークンなので、3,000 枚でも約 77 万トークン。テキストの索引と同じ規模で、G2（画像ごとに視覚モデルを呼ぶ）より安く、速い見込み（料金は、公式で確認する）。
- **PDF や音声**も、同じモデルなら、文字起こしや OCR を経ずに対象にできる。今回は範囲外にして、需要を見る。
- **検索**: `scrap search "梁の写真" --semantic --images`（テキストでの検索）と、`--like <画像>`（似た画像）。結果に、サムネイルと、参照しているノートを出す。

**推奨**:
- **G1 は、標準で入れる**（コストなし）。
- **クラウドのモデルを選んだ利用者には、G3 を最優先にする**（G2 より簡単で、安く、速い）。
- **ローカルだけの利用者には、G1 と G2**（ローカルの視覚モデルで説明を作る）。ローカルの G3 は、実行環境の検証がついてから。
- **Embedder の仕組みは、最初から画像の入力に対応させる**（P1 の段階でインターフェースだけ決め、実装は後から足せる）。

**G2 の設計**:
- **対象**: ノートが参照している画像のうち、OCR の文字が取れていないもの、または短いもの。参照されていない画像（assets に残った写真）も含める。画像のバイトのハッシュを鍵にして、同じ画像を二度処理しない。
- **使うモデル**: 既存の `config.vision`（「画像解析（OCR）」の枠）を共用する。**「画像をこのPCの外に出さない」（`ocrMode: on-device`）が、そのまま意味検索にも効く**: オンなら、ローカルの視覚モデル（Ollama の Gemma など）か、処理しない。クラウドの視覚モデルへ送る場合は、§8 とは別に、画像の同意を取る。
- **保存**: 説明と文字は、索引の中に持つ（ノートの Markdown は変えない）。2 台の端末で同じ画像を二重に処理して費用がかかるのを避けたいときは、説明を `assets/.captions.jsonl`（画像のハッシュごとに追記、Git で同期）に置く案がある。**既定にはせず、選べるようにする**（導出データがリポジトリに入るため）。
- **費用の見積もり**: 構築の前に、対象の枚数と概算を見せる（テキストの埋め込みより、1 件あたりが大きい）。月の上限は、テキストと別に持つ。
- **速度**: ローカルの視覚モデルは、1 枚あたり数秒以上かかる見込み（未測定）。空き時間に、少しずつ処理する（§7）。

**検索の結果**: 画像のヒットは、サムネイル、ファイル名、参照しているノート（日付と見出し）を出す。CLI は、相対パスと、参照元のノートを返す（`--images` で、画像を対象に含める）。

**設定画面**: 「画像も検索の対象にする」のスイッチを足す（既定はオフ）。中に、方式（「ノートの文字だけ（G1）」「画像の説明を作る（G2）」）、使う視覚モデル（既存の「画像解析」と同じ）、「画像をこのPCの外に出さない」との連動の表示を置く。

**範囲外**: 音声（assets の音声ファイルの文字起こしは、すでにノートに入る）、PDF、動画。

## 15. P1 の実装記録（2026-10-02）

**構成**（純 Go、CGO なし）:

| 場所 | 内容 |
|---|---|
| `pkg/embed` | `Embedder`（`ID`、`Dim`、`Caps`、`Embed(ctx, kind, []Input)`）。Ollama（`/api/embed`）、OpenAI 互換（`/v1/embeddings`）、Gemini（`batchEmbedContents`）、決定的なダミー（`NewFake`）。再試行（429/5xx、`Retry-After`、バックオフ）、応答サイズの上限、エラー文からの鍵の除去、別ホストへのリダイレクトの拒否。`IsLocal` は loopback だけ（LAN のホストは外部扱い）。 |
| `pkg/semindex` | チャンク化（`chunk.go`）、保存（`store.go`: manifest.json、chunks.jsonl、vectors.bin、ロック）、更新と再構築と状態（`index.go`）、検索（`search.go`）、設定の読み出しと同意（`config.go`）、索引の場所（`dir.go`）。 |
| `pkg/cli` | `scrap index`、`scrap search --semantic`（`semanticcmd.go`）。 |
| `tools/semindex-eval` | 実験の再現と評価（生成は Node、評価は Go。README に手順）。 |

**保存の方針**: 追記だけ。manifest が確定点で、その先のバイトは次の書き込みが上書きする（途中で止まっても壊れない）。同じ文のチャンクはベクトルを共有する（コピーしたノート、触っただけのファイルは、埋め込みが 0 回）。不要な行が 200 件超かつ 2 割超になったら詰める。manifest とファイルが合わなければ `ErrCorrupt`（索引は派生データなので、作り直す）。再構築は別フォルダに作って、完成したら入れ替える（それまで古い索引が使える）。

**チャンク化の版**（`ChunkerVersion`）は 3。上げた理由は 2 回:
- 1→2: 長い段落を文で切るとき、文の間の改行と空白を落としていた（ログの行が繋がり、`EndLine` も短くなった）。元の文章の切り出しにして直した。直すと、チャンク数が実験の Node 版と同じ 3,101 に揃った。
- 2→3: **文の区切りを、日本語と英語の書き方に合わせた**（`sentence.go`）。「。」「！」「？」と改行で切る。直後の閉じ括弧と引用符（`。」`、`）`）、続く「。。。」「？！」は、その文に含める（次のチャンクが `」` で始まっていた）。`「」` `『』` の中の「。」では切らない（`彼は「明日送る。」と言った。` は 1 文。改行で必ず戻すので、閉じ忘れが後ろを巻き込まない）。「、」では切らない（節は文の一部）。ただし**1 文がチャンクの上限の 2 倍を超えるときだけ**、読点（`、` `，` `；`、英語の `, `）の後ろで切る。英語は、`Mr.` `Dr.` `vs.` `Fig.` などの略語、頭文字（`J. Smith`）、`e.g.` `U.S.`、続く語が小文字（`etc. and`）、小数と URL（`3.5`、`example.com`）では、ピリオドで切らない。日本語の評価は変わらない（0.82 / 0.89 / 0.61 / 0.86）。

**長さの単位は文字数で、言語を区別していない。それでよいと実測で確かめた**。bge-m3 のトークン数を実測すると（Ollama の `prompt_eval_count`）、1 トークンあたり日本語は約 1.5〜1.9 文字、英語は約 4.0〜4.4 文字で、150 文字は日本語で約 80〜100 トークン、英語で約 35 トークンになる。そこで「英語はもっと長いほうがよいのでは」と考え、日本語版と同じ作りの英語版（`tools/semindex-eval`、`gen.mjs … en`）を作って測った。結果は、**英語でも 150 文字が最良**（ベクトルのみ + 字句 0.05 で hit@1 0.82 / hit@5 0.89 / MRR 0.86、日本語と同じ。250 文字で 0.64 / 0.86 / 0.76、375 文字で 0.64 / 0.82 / 0.72、500 文字で 0.61 / 0.75 / 0.68）。最適な長さは、トークン数ではなく「1 件の事実が 1〜2 文」という粒度に近い（合成データでは、正解の 1 文がどちらの言語でも 100〜170 文字）。したがって、トークン推定で長さを数える案は採らない。ただし合成データの傾向であり、実データでの再評価（§12）が条件なのは変わらない。

|---|---|---|---|---|
| ベクトルのみ（見出しあり、150 字） | 0.79 | 0.82 | 0.58 | 0.81 |
| **+ 0.05 × 字句（既定）** | **0.82** | **0.89** | 0.61 | **0.86** |
| + 0.10 × 字句 | 0.79 | 0.89 | 0.59 | 0.83 |
| ベクトルのみ（見出しなし） | 0.64 | 0.75 | 0.49 | 0.69 |

§2 の Node 版の結果（0.82 / 0.89 / 0.86）を、Go の実装が再現した。見出しあり 150 字で 3,019 → 3,101 チャンク（上の修正）。

- **速度**: 構築は 300 日分（3,101 チャンク）で約 33 秒（モデルの速度で、約 94 件/秒）。何も変わらない 2 回目は 0.056 秒（モデルを呼ばない）。検索 1 回は、CLI の起動、クエリの埋め込み、索引の読み込みを含めて約 0.2 秒。索引の読み込みと検索だけで、約 19〜48 ms。
- **索引の大きさ**: 3,101 チャンク（1,024 次元、float32）で 13.7MB。
- **本体への影響**（実測。HEAD の同じ設定のビルドとの差）: アプリの exe +0.26MB（18.11 → 18.38MB）、CLI の exe +0.32MB（8.41 → 8.73MB）。起動時の初期化は `semindex` が 16KB で 0 ms 台（`embed` は 88 バイト）。機能がオフのとき、プロセスもメモリも、ディスクも増えない（P1 はアプリから呼ばない）。

**実機で確かめたこと**（隔離したプロファイル、本物の Ollama のネイティブ経路、本物の CLI の exe）: 構築、2 回目の無料の実行、検索（意味、`--kind log`、識別子）、チャンク化の版が変わった索引への更新の拒否と `--rebuild`（その間、古い索引で検索できる）、新しいノートの単語検索での補完と `--update`、モデルを止めたときの単語検索への切り替え。

**日本語と英語が混在したときの検索（実測、bge-m3）**: 3 つのコーパス（日本語のみ、英語のみ、1 つのコーパスの中で正解の文・ばらまきの文・ログの言語が日本語か英語かをランダムに選んだ混在）を、150 文字・見出しありで測った。質問は、日本語、英語、日本語に英語の語が混ざったもの（8 問）。「他言語のノートを探す」指標は、質問と同じ言語で書かれた正解を順位から外し、他言語で書かれた正解だけで採点する（他言語の正解がない質問は除く）。

| 質問と対象 | 字句なし | 字句 +0.05（旧: 最大で割る） | 字句 +0.05（現: idf で割る） |
|---|---|---|---|
| 日本語のみ、日本語の質問（28 問） | 0.79 / 0.82 / 0.81 | 0.82 / 0.89 / 0.86 | 0.82 / 0.82 / 0.83 |
| 英語のみ、英語の質問（28 問） | 0.82 / 0.86 / 0.85 | 0.82 / 0.89 / 0.86 | 0.79 / 0.86 / 0.83 |
| 混在、日本語の質問 | 0.68 / 0.82 / 0.75 | 0.75 / 0.86 / 0.81 | 0.68 / 0.86 / 0.77 |
| 混在、英語の質問 | 0.79 / 0.82 / 0.81 | **0.57** / 0.86 / 0.68 | 0.82 / 0.89 / 0.84 |
| 混在、日英混じりの質問（8 問） | 1.00 / 1.00 / 1.00 | 1.00 / 1.00 / 1.00 | 1.00 / 1.00 / 1.00 |
| 英語の質問で、日本語のノートを探す（22 問） | 0.77 / 0.82 / 0.80 | **0.45** / 0.77 / 0.58 | 0.77 / 0.86 / 0.80 |
| 日本語の質問で、英語のノートを探す（16 問） | 0.31 / 0.31 / 0.34 | 0.25 / 0.31 / 0.30 | 0.31 / 0.31 / 0.34 |

（各セルは hit@1 / hit@5 / MRR。識別子の質問は、すべて 1.00。）

- **日英混じりの質問**（「goroutine の同時実行数を制限する書き方」）は、日本語のノートも英語のノートも見つかる（hit@1 1.00）。
- **英語の質問で日本語のノートを探す**のは、字句なしで 0.77（hit@1）。**日本語の質問で英語のノートを探す**のは、0.31 で弱い。bge-m3 では、方向によって差がある。クロスリンガルを重視する利用者は、Gemini Embedding 2 などでの比較が要る（未測定、決定 #9）。
- **字句の加点の割り方を変えた**（`SearchOptions.LexNorm`、既定は `idf`）。最初の設計は「候補の中の最高点で割る」（`max`）で、最良のチャンクが必ず重み全部をもらった。混在のコーパスでは、質問と同じ言語の「ありふれた語」を共有するだけのチャンクが加点され、他言語の正解を押し下げた（上の太字: 英語の質問の hit@1 0.79 → 0.57、他言語探し 0.77 → 0.45）。**「質問の全トークンを 1 回ずつ含むチャンクの点」で割る**（`idf`）と、共有が少ないチャンクの加点が小さくなり、どのケースでもほぼ中立になる。単一言語での利得（日本語の hit@5 0.82 と 0.89 の差は 28 問中 2 問）より、混在での害（約 0.2〜0.3）が大きいので、`idf` を既定にした。重みは 0.05 のまま（idf では、日本語と混在の日本語の質問は 0.2〜0.4 まで上げると少し良く、英語の質問は下がる。単一の既定値としては 0.05）。

**長い文章で検索したとき**: 意味検索は、**文章全体を 1 つのベクトルにして**索引と比べる（単語に分けて grep はしない）。単語や文字の分割を使うのは、次の 3 か所だけ。(1) 字句の加点（重み 0.05）: クエリの隣り合う 2 文字と英数字の語を、**索引済みのチャンクのメモリ上の本文**に数える。ファイルは読まない。コストはトークン数 × チャンク数に比例するので、**トークンは 128 までに制限**した（英数字の語は 32 まで先に取り、残りの枠に 2 文字の組をクエリ全体から等間隔で取る。約 120 文字までのクエリは影響を受けない）。(2) 未索引のファイル、(3) モデルや索引が使えないときの代替: どちらも単語の検索（`Terms`）で、**先頭の 8 語**だけを使い、全語がそろわなければ半分以上で拾う。長文でこの代替になると、後半の語は使われない。モデルに渡す長さの上限は設けていない（Ollama は文脈の長さで切る。OpenAI の 8,191 トークンを超えるとエラーになり、単語検索に落ちて理由が出る）。
