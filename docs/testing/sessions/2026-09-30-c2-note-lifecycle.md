## 道具の補足（この憲章のためにキットの上に足したもの。リポジトリは触っていない）

- 「ディスク」の模型: モックの `saveFile` は何も残さず、`readFileByPath` は最初のノートを返し続ける。そこで `window.backend.saveFile / saveFileAs / readFileByPath` を頁の中で包み、書かれた内容を `window.__disk` と `__diskLog` に残した（`lib.mjs` の `installDisk`）。障害注入（`s.setBackend`）は包みの内側でそのまま効く。
- 「外部エディタ」: `window.__disk[path]` を書き換え、Go の監視と同じく `window.__onExternalFileChanged(path)` を呼ぶ（`externalWrite`）。
- 「再起動」: `beforeunload` を手で送って、バックエンドが最後に受けた `saveSession` の文字列を取り、同じブラウザでページを読み直す。読み直しの時だけ、ブートデータの `session` と `noteFiles` を差し替える初期スクリプトを足した（`restart`）。強制終了の模擬は `beforeunload` を送らずに最後の `saveSession` を使う。
- Ctrl+W / Ctrl+O / Ctrl+Shift+S は、頁の keydown を直接送った（`ctrlW`、`synth`）。理由は下のログ e2 と C2-12。

### C2-01 追記の通知（CLI パイプ・クイックキャプチャ・ホットフォルダ・Discord）が、開いているスクラップの未保存の入力を黙って捨てる

- 重大度（案）: P0（データを失う。自動保存オンでも、追記が打鍵の 1.5 秒以内に届くか、自動保存が止まっている時に起きる）
- 気づきの型: WI
- なぜ気づけたか: ハンドラを読んで、「タブが dirty の時に通知が来たらどうなる？」と問うた。`onScrapAppended` と `onDiscordBridgeMessage` は、ディスクから読んだ文字列でタブの内容を置き換え、そのまま `isDirty = false` にする。
- 再現手順:
  1. 今日のスクラップ（保存済みのファイル）を開き、末尾に 1 行打つ（自動保存の前、または自動保存オフ）。
  2. ディスクに 1 行追記されたあと、`window.onScrapAppended({filePath, fileName, command})` を呼ぶ（本物では Go の `app_scrap.go` / `app_inbox.go` / クイックキャプチャが呼ぶ）。`window.onDiscordBridgeMessage` でも同じ。
  3. タブの中身、dirty、Ctrl+Z を見る。
- 期待（オラクル）: 打った行は残る（未保存の内容と新しい追記を合わせる、または確認する）。「データを失わない」（計画 §6 の P0）。
- 実際: 打った行が消え、タブは clean になり、トーストは「Scrap appended: pipe」または「Added from Discord」だけ（消えたことは伝わらない）。Ctrl+Z でも戻らない（`editorEl.value` を直接書くため）。
- 環境: 版 1.10.5（HEAD a8bfea5）· Windows 11 · 探索キット（ハーネス）· 英語
- 再現性: 毎回（4 回中 4 回: 自動保存オン、自動保存オフ、Discord、Ctrl+Z の確認）
- 証拠: EV `e10.out`、`e10_autosave-on-fast.png`、`e10_autosave-off.png`、`e10_discord-autosave-off.png`、`e10_*.json`、`e11b.json`

### C2-03 保存確認ダイアログを 2 重に開くと、キー入力の監視が残り、あとで打った d / n / s / Enter / Esc がノートを閉じる

### C2-04 保存の待ち中に打った文字が、保存後に「保存済み」として扱われる（dirty が消える）

- 重大度（案）: P1（データを失う。窓は保存の往復の間だけ。ローカルディスクでは数 ms、共有ドライブや同期フォルダでは長い）

## 未再現・確かめられなかったもの

- `SaveFile` / `SaveSession` の非同期でない書き込み（`os.WriteFile` はその場で切り詰めて書く）: ディスクが満杯・強制終了のとき、ファイルが空または途中で切れて残る可能性。コードを読んだだけで、キットには本物のファイルシステムがないため再現していない（C2-11 の原因にも関係）。
- Ctrl+W の自動連打が実 WebView2 で 2 つ目の確認ダイアログを開くか（C2-03 の引き金の現実性）。
- 保存が同時に 2 回走ったときの順序（キットの遅延は「呼び出しの前」に入るので、順序の入れ替わりを正しく模擬できない。WebView2 の呼び出しは UI スレッドで順に走るので起きにくいと見ている）。

## 問題が見つからなかった領域（誠実な「なし」）

- 基本の一生（新規 → 編集 → 名前を付けて保存 → 自動保存 1.5 秒 → 通常終了 → 復元）: 内容、caret、パス、タイトルとも問題なし。
- 唯一のタブが dirty で、保存が失敗するときの Ctrl+W: ダイアログが閉じ、ウィンドウは閉じず、トーストが出て、タブは残る。
- 保存の取り消し（Save As を取り消す）: dirty のまま、無言（普通）。
- 強制終了の窓: セッションは最後の打鍵の約 0.5 秒後に書かれる。失うのは最後の約 0.5 秒の入力だけ。
- 即時表示と遅れて届くセッションの競合: 返事が 0.6〜1.5 秒遅れても、すぐ打った文字は残る（2 回）。
- 初回の Welcome ノートの一生: 打った 1 行は終了・再起動後も残り、タブは 1 つ。
- 二重の確認ダイアログを、キーボード（S）で答えた場合: 2 回保存されるが、内容は正しく無害。

## 振り返り（5 分）

- 学んだこと（次に同じ型で探すときのヒント）: 「置き換え」を探す。`content = 読んだ文字列; isDirty = false` の形（`onScrapAppended`、`onDiscordBridgeMessage`）、`await` のあとに状態を下ろす形（`saveTab`）、Promise を返す関数が `window` にリスナーを足す形（`confirmSaveDialog`）は、どれもコードを読むと見つかった。そして「同じ意味の RPC 側は正しく作られている」という食い違い（`commitSave`、`tab.open`）が、画面側の不具合の目印になった。保存・上書きの実装がある場所は、コードを読んでから触ると当たりが多い。
- 次にやる憲章: (1) 分割ペイン × 同じノートを両側で保存（C5 と重なる）。(2) 巨大ノート（C4）の保存とセッション書き込みの所要時間（`saveSessionDebounced` が全タブの本文を毎回書く）。(3) C2-01 と C2-02 の修正後に、クイックキャプチャ・ホットフォルダ・Discord の各入口で同じ確認。
