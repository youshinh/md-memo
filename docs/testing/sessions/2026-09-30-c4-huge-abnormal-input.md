### C4-01 複数行の大きな挿入は行数の 2 乗で遅く、AI の答え・CLI の書き込み・HTML 貼り付けの間ずっと画面が固まる

- 重大度（案）: P1（テンプレートの定義では「固まる」なので P0 にもなりうる。実 WebView2 と実際の CLI で確かめるまで P1 とする）
- 気づきの型: WI
- なぜ気づけたか: `setBuffer` で 5,000 行を入れたら 31 秒返らなかった。「`execCommand` は行ごとに分かれて実行されるのでは」という内部の疑いから、素の textarea と比べた
- 再現手順:
  1. 探索キットで 1 タブのノートを開く。`llm: { mode: 'huge', lines: 4000, delayMs: 100 }`
  2. 全選択して Ctrl+L → `expand` → Enter
  3. ページの心拍か longtask を見る
- 期待（オラクル）: 数百 ms で入る（`setRangeText` は 2 万行で 160 ms）。少なくとも数万行が数分固まることはない
- 実際: 500 行 0.28 秒、1,000 行 1.5 秒、2,000 行 4.9 秒、4,000 行 16 秒（1 つの longtask）。`setBuffer` は 5,000 行で約 31 秒、8 万行は 220 秒待っても返らない。素の textarea の `execCommand('insertText')` は 250 → 500 → 1000 → 2000 行で 66 → 209 → 776 → 2,946 ms（倍で約 4 倍）。CDP の `Input.insertText` も 1000 行 1.1 秒、4000 行 17.7 秒、16000 行は 210 秒待っても返らない。**200 行ずつ 10 回に分けても 2,070 ms で、分割しても効かない**。既に 2000 行あるところに 200 行足すと 417 ms、空なら 43 ms（コストは「入れる行数 × 既にある行数」）。`setRangeText` は 2000 行 20 ms、2 万行 160 ms（ただし Ctrl+Z の履歴に入らない）。Ctrl+Z は 47〜244 ms で速く戻る
- 環境: 1.10.5 · Windows 11 · 探索キット（headless Edge）· 英語（日本語 UI でも同じ）
- 再現性: 毎回（6 回以上。C1 の g1/g2、C7-01 も別々に同じ結果）
- 証拠: 証拠置き場の `p1.mjs` `p3.mjs` `ai1.mjs` `p2.mjs` の出力（このログの表）
- 原因の仮説: `execInsertTextExact` が複数行の文字列を `document.execCommand('insertText')` に渡す。入口は `replaceAnchorWithUndo`（AI の答え）、`writeTabText`（CLI の `buffer set/append`）、`insertPastedText`（HTML → Markdown の貼り付け）、コマンドフィルタの結果など多数。Undo を残したまま速くするには、ある行数（数百行）を超えたら `setRangeText` と、アプリ側の 1 段の元に戻す記録に切り替える案がある（コストは「入れる行数 × 既にある行数」なので、入れる側を分割しても直らない）
- 自動テストにできるか: できる（`tests/huge_note_perf_test.mjs` に「N 行の挿入が 500 ms 以内」の閾値つきテストを加える。探索キットで longtask を見る形のスモークも可）。ただし実 WebView2 の値は実機でしか確かめられない

### C4-02 検索ボックスで Enter を押すと編集領域にフォーカスが移り、続けてもう一度 Enter を押すと選択された一致が改行に置き換わる

- 重大度（案）: P1（自然なキー操作で、気づかないうちに文字が消える。Ctrl+Z では戻る）
- 気づきの型: NV
- なぜ気づけたか: 10 MB の 1 行のテストで「最後の一致へ」を押したらノートが 1 文字増えた。小さなノートで組み合わせを絞ったら、検索の Enter とフォーカスの組み合わせだと分かった
- 再現手順:
  1. `fox one / fox two / fox three` の 3 行のノートで、キャレットを先頭に置く
  2. Ctrl+F → `fox` と入力
  3. Enter（1 回目）→ Enter（2 回目）
- 期待（オラクル）: 他のエディタ（検索ボックスでの Enter は次の一致に進み、フォーカスは検索ボックスに残る）。2 回目の Enter で 2 番目の `fox` に移る
- 実際: 1 回目で `fox` が選択されフォーカスが `#editor` に移る（`goToMatch` の `editor.focus()`）。2 回目の Enter は編集領域の普通の Enter として働き、選択された `fox` が改行に置き換わる（`fox one` → `\n one`）
- 環境: 1.10.5 · Windows 11 · 探索キット · 英語・日本語
- 再現性: 毎回（3 回中 3 回: F2、F3 の英語、F3 の日本語）
- 証拠: 証拠置き場の `f2.mjs` `f3.mjs` の出力
- 原因の仮説: `goToMatch` が一致を選ぶたびに `editor.focus()` を呼ぶ。検索の Enter は `keydown` で `preventDefault` されるだけなので、フォーカスの移った先で次の Enter が働く
- 自動テストにできるか: できる（ダム DOM の `createEnv` で Ctrl+F → Enter ×2 の後のノート本文を確かめる）

### C4-03 「置換」「すべて置換」と、複数行の Tab / Shift+Tab は Ctrl+Z で戻らず、その前の入力の履歴も消える

- 重大度（案）: P1（ノート全体に効く操作が取り消せない。Ctrl+/ や AI の結果は戻せるので、利用者は戻せると思っている）
- 気づきの型: OR（Ctrl+/ など他の操作が戻せることと食い違う）
- なぜ気づけたか: 8 万行のノートで「全選択 → Tab」を試したあとに Ctrl+Z を押すと何も起きなかった。同じ `.value =` の箇所が検索にもあることをコードで探した
- 再現手順:
  1. 3 行のノートに `alpha / beta / gamma` と打つ
  2. Ctrl+A → Tab（4 つの空白でインデント）→ Ctrl+Z を 2 回
  3. 別の実行で、`foo bar foo` と打ち、Ctrl+H で `foo` → `Q` の「すべて置換」→ Ctrl+Z を 2 回
- 期待（オラクル）: インデントも置換も 1 回の Ctrl+Z で戻る（他の操作は戻る: Ctrl+/ は戻った。AI の答えも戻る）
- 実際: Ctrl+Z を何度押しても変わらない。事前に打った `>> ` も戻せなくなる（履歴ごと消える）
- 環境: 1.10.5 · Windows 11 · 探索キット · 英語・日本語
- 再現性: 毎回（5 回中 5 回: U1 の小さなノート、U1b の 8 万行、Z2、Z3 の英語・日本語）
- 証拠: 証拠置き場の `u1.mjs` `z2.mjs` `z3.mjs` の出力
- 原因の仮説: `applyTabIndent`（複数行と Shift+Tab）、`replaceOne`、`replaceAll` が `editor.value = ...` を代入する。textarea は値を代入すると元に戻す履歴を全部捨てる。他の行操作は `execCommand`（`insertTextWithUndo`）を使っている
- 自動テストにできるか: できる（`createEnv` に元に戻す履歴のあるモデルを足して、これらの操作の後に undo が使えるかを確かめる。今の `createEnv` は undo の履歴を持たないので、`tests/ai_lifecycle_fuzz_test.mjs` の undo つきの箱を使う）

### C4-04 検索ボックスの Shift+Enter（前を検索）で、ノートに空行が挿入される

- 重大度（案）: P2（Ctrl+Z で戻る。ただし検索の最中に気づかず文が動く）
- 気づきの型: OR
- なぜ気づけたか: 10 MB の 1 行のテストで、C4-02 の調査中に見つけた（長さが 1 増えていた）
- 再現手順:
  1. `fox one / fox two / fox three` のノートでキャレットを先頭に置き、Ctrl+F → `fox`
  2. Shift+Enter（前を検索）
- 期待（オラクル）: 前の一致に移る。ノートの本文は変わらない
- 実際: 一致を選んだあと、同じキー押しで「下に行を挿入」（既定 Shift+Enter）が新しいフォーカス先（編集領域）に対して実行され、行末に改行が 1 つ入り、キャレットがそこへ移る（`fox one\n\nfox two`）。Ctrl+Z で戻る

- 学んだこと: (1) 「巨大な入力」は、アプリのコードではなく**ブラウザの編集コマンドの性質**（複数行の `insertText` が行数の 2 乗）に当たった。素の textarea を「対照」として同じページに置くと、アプリの分とブラウザの分が 1 回で分けられる。(2) 「大きな入力」の探索から、検索、置換、Tab のような**小さな入力でも起こるバグ**（C4-02〜C4-06、C4-17）が出た。大きな入力は組み合わせを増やすきっかけとして働く。(3) 大きなノートを扱うと、キットの `state()`（全タブの全文を返す）が返らなくなる。軽い `probe()` を自作した。(4) `\\` を含むスクリプトはシェルの here-document だと化けるので、ファイル書き込みのツールを使うこと。
