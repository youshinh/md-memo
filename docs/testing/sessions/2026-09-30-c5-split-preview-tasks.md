### C5-01 `{{ }}` スロットの結果が、実行した「ノート」ではなく、今そのペインに見えている「ノート」に書き込まれる

- 重大度（案）: P0（別のノートの本文を上書きし、自動保存が有効ならディスクにも書かれる。元のノートには「実行中」の表示が残る）
- 気づきの型: RC
- なぜ気づけたか: 計画 §3.1 の 9（分割ペイン × 片方を閉じる × タスク実行中）を試すために `applyMergeToEditor` を読んだところ、結果の行き先が `meta.editor`（ペイン）で、タブ ID を使っていなかった。
- 再現手順:
  1. a.md に `{{ write a haiku }}`、b.md に数行を書いて開く。
  2. a.md の `{{ }}` の中に caret を置いて Ctrl+Enter（目印が `{{ ⟳ 実行中... }}` になる）。
  3. エージェントの答えが来る前に、タブ b.md をクリックして左ペインを b.md にする（右ペインで実行した場合は、右ペインのタブを c.md に切り替える / 右ペインを閉じて別のノートで開き直す / タブを閉じる、でも同じ）。
  4. 答え（`status: completed`、`outputMode: replace`、Go と同じオフセット）が届く。
- 期待（オラクル）: 結果は実行したノートに入る。関連コード自身が「実行したペインへ戻す」と書いていて、取り消しの側（`runNote` / `editorShowing`）は `meta.tabId` でノートを探している。AI 質問と `{{ @agent }}` の結果はタブ ID で正しく動く（対照 X1、X2）。
- 実際: b.md の「beta three」の途中など、元のオフセットの 19 文字が答えで置き換わる（`betHAIKU-TEXTta four`）。a.md には `{{ ⟳ 実行中... }}` が残ったままで、そこへの再実行は「すでに実行中」と言われる。タスク一覧は「完了」。自動保存をオンにした保存済みノートでは、壊れた本文が 1.5 秒後に `saveFile` へ渡された（s20）。
- 環境: 版 1.10.5 · Windows · 探索キット（ヘッドレス Edge + モック）· 英語 UI
- 再現性: 毎回（5 回中 5 回: s03、s04 の V2 / V3 / V4、s20）

### C5-02 ペインを閉じる / プレビューに切り替えたあとで `{{ }}` の結果が届くと、フォーカスのある別のエディタの caret 位置に答えの文字が余分に挿入される

- 重大度（案）: P0（別のノートに、利用者が書いていない文字が入る。自動保存が有効なら保存される）
- 気づきの型: WI
- なぜ気づけたか: 「隠れた（display:none の）テキストエリアで `focus()` と `execCommand('insertText')` をするとどうなるか」という内部からの問い。実際は s12 の出力で、正しいノートのほかに左の a.md にも同じ文字が入っているのを見て発見した。
- 再現手順:
  1. 左 a.md、右 b.md（タブ b.md を Alt+クリック）で分割する。
  2. 右ペインの b.md にある `{{ write a haiku }}` の中で Ctrl+Enter。
  3. 右ペインを閉じる（×ボタンでも分割トグルでも可）。または、右ペインを「プレビュー」に切り替えてから左のエディタをクリックする。
  4. エージェントの答えが届く。
- 期待（オラクル）: 答えは b.md にだけ 1 回入る。左のノートは変わらない。
- 実際: b.md には正しく入るが、左の a.md の caret 位置に答えの文字（`HAIKU-X`）も入る。タブが 2 つとも未保存（`*`）になる。ステータスは「Task: Done」（EV `s18-w1-stray-insert.png`: 1 行目が `HAIKU-X# Alpha`）。
- 環境: 版 1.10.5 · Windows · 探索キット · 英語 UI
- 再現性: 毎回（4 回中 4 回: s12 の H1、s13 の W1 と W2、s14 の W4b）。同じノートを左右に開いている場合は余分な挿入はなく正しい（s13 の W3）。フォーカスがどのエディタにもない場合（右をプレビューにしただけ）も余分な挿入はない（W4）。
- 証拠: `s18-w1-stray-insert.png`、`s14-w4b.png`、`log-s12.json`、`log-s13.json`、`log-s14.json`
- 原因の仮説: `replaceRangeWithUndo(editor, ...)` は `editor.focus()` のあと `document.execCommand('insertText')` を使う。隠れたエディタは `focus()` できないので、命令は今フォーカスのあるエディタ（左）に対して実行され、`true` を返す。そのあと `editor.value !== expected` の補正が右のエディタだけを直すため、左の余分な挿入は残る。C5-01 と同じ原因（ペインに結び付けている）に根がある。
- 自動テストにできるか: できる（模擬環境で、隠れたペインを `meta.editor` に持つ結果を渡し、他のエディタの値が変わらないことを確かめる）

### C5-03 2 つの `{{ }}` を同時に実行して 2 番目の答えが先に届くと、答えが 1 番目の場所に入る

- 重大度（案）: P1（答えが入れ替わる。気づかないと別の指示の答えを読んでしまう。まれには本文が入れ替わる）
- 気づきの型: WI
- なぜ気づけたか: `applyMergeToEditor` の「開始位置 - 40 文字から `executingText`（全スロットで同じ `{{ ⟳ 実行中... }}`）を探す」検索窓が、同じ見た目の目印が近くに 2 つあるときに先頭のものを拾うはず、という読み。
- 再現手順:
  1. `{{ first task }}` と `{{ second task }}` を隣り合う行（または数行離れた行）に書く。
  2. 1 番目、2 番目の順に Ctrl+Enter（両方 `{{ ⟳ 実行中... }}` になる）。
  3. 2 番目の答えを先に渡す。次に 1 番目の答えを渡す。
- 期待（オラクル）: 各答えは、自分が実行したスロットの場所に入る。
- 実際: 2 番目の答え `ANSWER-2` が 1 番目の場所に入り、1 番目の答え `ANSWER-1` が 2 番目の場所に入る。編集がなくても起き（s11 の S1）、上に 30 文字や 400 文字を入れても起きた（S2、B1）。
- 環境: 版 1.10.5 · Windows · 探索キット · 英語 UI
- 再現性: 毎回（3 回中 3 回: s10 の B1、s11 の S1 と S2）
- 証拠: `log-s10.json`、`log-s11.json`

## 確かめて問題がなかったこと（対照）

- 質問（Ctrl+L）、`[[ @llm ]]`、`{{ @agent }}`（下に書く形）の結果は、ペインの入れ替え・ペインを閉じる・タブを閉じるの後でも、質問したノートにだけ正しく入る（X1、X2、K1）。
- 同じノートを左右に開いたときの結果ブロック（目印 2 行 + 本文）は両ペインで一致し、ガターの緑の棒も一致する。再実行でブロックが重ならない（s05）。
- 同じタスクを左右から続けて Ctrl+Enter しても要求は 1 件（G1）。タスク一覧からの中断で、ノートは厳密に元に戻る（C1）。
- 保存済みノートの背景タブで答えを受けると、自動保存が働く（P2）。
- 折り返した行の下に着いた答えの帯は、位置と高さが正しい（s09）。
- 全画面プレビュー中の Ctrl+L は、隠れたエディタの選択を対象に動き、答えは 1 回だけ入ってプレビューも更新される（s06）。
- 結果ブロックの Esc は、`[[ @llm ]]` の結果には何もしない（計画のライフサイクルにある「元に戻す（Esc）」は旧記法のスロットだけ。仕様かどうかは未確認）。

## 振り返り（5 分）

- 学んだこと（次に同じ型で探すときのヒント）:
  - 「結果が来る」処理は、行き先を「ペイン（テキストエリア）」で持つものと「ノート（タブ ID）」で持つものが混ざっている。前者は旧記法の `{{ }}`、パレットの命令、`showAskFailure` の判定だった。新しい機能を足すたびに、行き先の持ち方を確かめる価値がある。
  - 「隠れたテキストエリアに `focus()` と `execCommand`」は、フォーカスのある別の要素に書いてしまう。ほかに `replaceRangeWithUndo`、`insertTextWithUndo` を隠れたエディタに使う箇所がないか、grep で洗うとよい。
  - 「同じノートを左右に開く」は特殊な状態で、値の丸ごと代入で caret が飛ぶ。値の代入があるところ（`editorSecondary.value = ...`）を洗うとよい。
- 次にやる憲章: C5 の続きとして、(a) Quick Actions（Ctrl+J）と `[[ $ ]]` コマンドタスクの結果を分割の各状態で受ける、(b) パレットの他の命令（日付、コメント、Mermaid）が左に効くか、(c) レシピ `[>> ]`、(d) 実 WebView2 で隠れたエディタの `focus()` と `execCommand` が同じか（探索キットは Edge なので同じ挙動のはずだが実機では未確認）。
- 自動テストにできるもの: C5-01、02、03 は `slot_agent` の合成テスト（ペインの入れ替え・閉じる・隣り合う 2 つの目印）。C5-04 はパレットの項目を `activePane = 'secondary'` で実行する。C5-05〜09 は分割の模擬環境。探索キットに「エージェントの結果を渡す」口（`s.deliverSlot`）を足すと、この憲章の再現が 1 行になる。
- うまくいかなかったこと（道具・進め方）: `s.state()` は左のエディタだけなので、右ペイン・プレビュー・帯・タスク一覧を含む自前のスナップショット（`h.mjs`）を作った。キットに右ペインの状態が入ると探索が速くなる。モックの `ghost_diff_duration_ms` が 8000 で、帯が消える場面が見えにくい。`s.ev` で作ったパスの文字列（`\\`）はシェル経由だと崩れやすい（`/` を使った）。s15 のパレット操作は最初に手順を誤り（項目名が違う）、s16 で確かめ直した。

## 確かめられなかったこと
