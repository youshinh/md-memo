三つの視点の当て方:
- 名詞 × 動詞: 表・見出し × キャレットの位置 × 続けて貼る、画像 × OCR あり・なし・ローカルモデル × 続けて貼る × タブ切り替え、ファイル × 貼る / ドロップ、Ctrl+V × Ctrl+Shift+V

### C8-01 OCR の失敗で、API キーを含む生のエラー行がノートに書かれ、自動保存でファイルに残る

- 重大度（案）: P1 ― 根拠: 秘密がユーザーデータに入る。Git 同期するスクラップのフォルダなら外に出うるので P0 に近い。オフラインの PC で画像を貼るだけで起きる
- 気づきの型: WI
- なぜ気づけたか: Gemini の URL は `...:generateContent?key=<キー>` で、Go の `http.Client.Do` のエラー文は URL をそのまま含む（コードとスクラッチの Go 呼び出しで確認）。質問バーは D1 で生のエラーをノートに入れなくなった（`llm_error.js` の冒頭に「以前はそのまま書かれた」とある）のに、画像 OCR の経路（`__onLLMResult` の `vision_` 分岐）は `[LLM error: <生の文言>]` を入れる
- 再現手順:
  1. 既定の設定（視覚 = Gemini、キーあり、`pasteImageOcr` オン）。パス付きのノートで、キャレットを末尾に置く
  2. 画像をクリップボードに置き、Ctrl+V
  3. 視覚の要求が失敗する（キットでは `s.setLlm({ mode: 'fail', error: 'Gemini接続エラー: Post "https://generativelanguage.googleapis.com/v1beta/models/gemini-flash-lite-latest:generateContent?key=AIzaSyFAKE-KEY-FOR-TEST-0000": dial tcp: lookup ...: no such host' })`）
  4. 1.5 秒待つ（自動保存）
- 期待（オラクル）: 質問バーの失敗（D1）と同じく、ノートは元のまま。理由は平易な言葉で。秘密（キー）は、ノートにも画面にもファイルにも出ない
- 実際: ノートの末尾に `[LLM error: Gemini接続エラー: Post "https://...?key=AIzaSyFAKE-KEY-FOR-TEST-0000": dial tcp: ...]` が入り、トーストとステータスバーにも 5 秒出る。自動保存で `saveFile` が呼ばれ、その内容にキーの入った行がある（e12 の `saveFile raw`）
- 環境: v1.10.5 作業ツリー（`a8bfea5`）· Windows · 探索キット · 英語 UI。実際の Go のエラー文は `gocheck/main.go`（リポジトリ外）で確認
- 再現性: 毎回（3 回中 3: e3-J、e11-J2、e12）

### C8-20（道具）探索キットの制約 3 点

- 重大度（案）: P3（アプリではなくキット）
- 気づきの型: ENV
- なぜ気づけたか: 実行が返らなくなった
- 内容: (1) `s.state()` は全タブの本文を返すので、数 MB のノートがあると戻ってこない（ノードもブラウザも CPU 0 で待つ）。(2) headless では `Ctrl+W` がブラウザ側でタブを閉じ、以降すべての評価が返らない。(3) `Ctrl+Tab` はアプリのタブを切り替えない（実マウスでタブをクリックすると切り替わる）。(4) 合成の貼り付け・ドロップは、既定の挿入や実 WebView2 の権限ダイアログを再現しない
- 再現性: 毎回（(1) 3 回、(2) 2 回、(3) 2 回）
- 原因の仮説: (1) `tools/docshots/cdp.mjs` の WebSocket の受信、または戻りの大きさ。(2)(3) headless のブラウザのショートカット
- 自動テストにできるか: キットの README に注意書きを足す。`state()` に `contentMax` を付ける

## 再現できなかったもの · 確かめられなかったもの

- 文字だけのドラッグ（URL・選択した文字）を編集領域に落とすと、window の `drop` ハンドラが既定の動作を止めるので、実物では挿入されない可能性がある（キットでは `dragover` / `drop` とも `defaultPrevented: true`、ノート無変化を 2 回確認）。CDP の `Input.dispatchDragEvent` でも素の textarea が挿入しなかったので、実 WebView2 での結果は未確認。
- 平文 2 MB の貼り付けが 14〜18 秒（1 回目 14 秒、2 回目 18.5 秒）。キットの代替挿入が `execCommand` なので、実物のネイティブ貼り付けの速さとは比べられない（HTML から変換した Markdown を入れる経路 C8-03 は実物と同じ）。
- 入れ子 3 万段の div / 5 千段の ul は変換が例外で落ち、平文に黙って戻る（テキストは入る）。通知がない点は記録のみ。
- 待ち中にタブを閉じたときの「AI working (1)」の残り（e4-G）は、答えが届けば 0 に戻る。`never` だと 180 秒残る。1 回だけ。

## 振り返り（5 分）

- 学んだこと: 「同じ文字のアンカー」「入口が違う 2 つの経路（Ctrl+V の OCR / 保存、ask バー）」「失敗文を素通しで書く」の 3 つは、コードを読んでから試すと効率よく当たる。ask バーで直した D1 の考え（生の文言をノートに書かない）が OCR に届いていない。挿入の遅さは C1 の AI の答えと同じ根（`execCommand`）で、貼り付けの経路でも起きる
- 次にやる憲章: (1) OCR・音声・ホットフォルダ・Discord など「画像や音が入る経路」の失敗の書き方の総点検（生のエラー文とキー）。(2) `execCommand` の挿入を使う全経路（貼り付け・答え・置き換え）の大きさ別の時間。(3) 実 Word / Excel / ブラウザのクリップボードの形の採取（実機）
- 自動テストにできるもの: (a) Go: `pkg/llm` の視覚・テキストのエラー文にキーが入らない。(b) JS: fuzz に「画像の貼り付け」を足す（順序、失敗、undo、秘密を含まない）。(c) `html_to_md_test.js` に結合セル・`_` の URL・NBSP・入れ子の表・`<style>` 多数。(d) `decidePasteAction` の表にファイルのみ・特別貼り付けの残り。(e) 「表を貼ったあと・キャレット位置別」の改行の規則
- うまくいかなかったこと（道具・進め方）: `s.state()` の制約（C8-20）で、数回の実行が返らなくなり、自分のブラウザの孤児を手で片づけた。Ctrl+W は headless でタブを閉じる。最初に巨大な貼り付けを一括で走らせたため原因の切り分けが遅れた（1 ケースずつ別セッションにすべきだった）。Word / Excel の実クリップボードは採れず、手作りの近似で試した
